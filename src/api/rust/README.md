# bitwuzla (Rust)

Safe, high-level Rust bindings for the [Bitwuzla](https://bitwuzla.github.io)
SMT solver.

| Crate             | Description                                          |
|-------------------|------------------------------------------------------|
| `bitwuzla`        | Safe, idiomatic Rust API (this directory)            |
| `libbitwuzla-sys` | Raw FFI bindings for the C API, generated by bindgen |

The safe API is modeled on the C++ API and implemented on top of the C API.

## Building

`libbitwuzla-sys` needs a Bitwuzla library and libclang (for bindgen). It looks
for Bitwuzla in this order:

1. `BITWUZLA_LIB_DIR`: a directory containing `libbitwuzla`; headers are
   taken from `BITWUZLA_INCLUDE_DIR`, `$BITWUZLA_LIB_DIR/../include`, or the
   enclosing source tree.
2. `BITWUZLA_BUILD_DIR`: a meson build directory of a Bitwuzla checkout.
3. `build/` of the enclosing Bitwuzla source tree, if it provides the
   requested kind of library (shared, or static with the `static` feature).
4. pkg-config (`bitwuzla.pc`, honors `PKG_CONFIG_PATH`).

Bitwuzla must be at least as new as the crates: the bindings of version
`x.y.z` need Bitwuzla `x.y.z` or newer, where a development version such as
`x.y.z-dev` counts as newer than release `x.y.z`. The build fails for an older
library. At run time, the library must be of the release the crates were built
against (all releases share the soname `libbitwuzla.so.0`, but may renumber C
enum values), otherwise the first API call panics.

Within a Bitwuzla checkout:

```sh
./configure.py --shared
cd build && meson compile && cd ..
cd src/api/rust
cargo test
```

When linking against a shared library on Unix, the build script makes the
library available to `cargo test` and `cargo run`; other binaries (and all
binaries on Windows) need it on the dynamic library path (or an rpath). The
`static` feature links Bitwuzla statically and requires `libbitwuzla.a`
(e.g., `./configure.py --static`), otherwise a shared library is required.

## Example

```rust
use bitwuzla::{Bitwuzla, Kind, Opt, Options, SatResult, TermManager};

fn main() -> bitwuzla::Result<()> {
    let tm = TermManager::new();
    let mut options = Options::new();
    options.set(Opt::ProduceModels, true)?;
    let mut bitwuzla = Bitwuzla::new(&tm, &options)?;

    let bv8 = tm.mk_bv_sort(8);
    let x = tm.mk_const(&bv8, "x");
    let y = tm.mk_const(&bv8, "y");
    let three = tm.mk_bv_value_u64(&bv8, 3);
    let sum = tm.mk_term(Kind::BvAdd, &[&x, &y], &[]);
    bitwuzla.assert_formula(&tm.mk_term(Kind::Equal, &[&sum, &three], &[]));
    bitwuzla.assert_formula(&tm.mk_term(Kind::BvUgt, &[&x, &y], &[]));

    assert_eq!(bitwuzla.check_sat()?, SatResult::Sat);
    println!("x = {}", bitwuzla.get_value(&x).value_str(10));
    println!("y = {}", bitwuzla.get_value(&y).value_str(10));
    Ok(())
}
```

`examples/` contains ports of the C++ API examples in `examples/cpp` of the
Bitwuzla source tree, e.g.:

```sh
cargo run --example quickstart
```

`examples/c/manual_reference_counting.c` has no port: sorts and terms are
released when dropped.

## API overview

- `TermManager`: creates sorts and terms.
- `Sort`, `Term`: sorts and terms.
- `Options`, `OptionInfo`: solver configuration.
- `Bitwuzla`: the solver.
- `Parser`: SMT-LIB v2 and BTOR2 parser.
- `Terminator`: early termination of solver calls (implemented for closures).
- `Kind`, `RoundingMode`, `Opt` (C/C++ `Option`), `SatResult` (C/C++ `Result`):
  enums generated from the C API headers, each with an `ALL` array and
  conversions to and from the C API's integer values. `Kind`, `RoundingMode`
  and `SatResult` implement `Display` with Bitwuzla's names (`BV_ADD`, `RNE`,
  `sat`), like `operator<<` and `std::to_string` in the C++ API.
- `sys`: the raw C API (`libbitwuzla-sys`), with C names.

### Differences to the C++ API

- Where the C++ API throws, the Rust API returns `Err` or panics, see
  [Errors and panics](#errors-and-panics). There are no null sorts or terms.
- Sorts, terms, solvers and parsers keep their term manager alive (reference
  counted), so no type carries a lifetime. Term managers, sorts, terms,
  options, solvers and parsers are neither `Send` nor `Sync`: they share
  unsynchronized state, e.g., the sorts and terms of a term manager, so each
  must stay on the thread that created it. Separate term managers, each with
  its own options, solvers and parsers, can be used on separate threads.
- Printing returns `String`s; bit-vector output format is given as a `base`
  argument instead of a stream manipulator.
- `Options::set` takes a `bool` for Boolean options and an integer for
  numeric options, which are not interchangeable. The C++ `set` overloads for
  option names and command line arguments are `Options::set_by_name` and
  `Options::set_args`.
- `Parser::parse` is split into `parse_str` and `parse_file` (any
  `AsRef<Path>`), and its `parse_only` argument is a parser setting,
  `Parser::configure_parse_only`.
- A `Terminator` runs in the middle of a solver call and must not use
  Bitwuzla objects other than to clone or drop them: any other call into
  Bitwuzla from a terminator panics.
- Not available (no C API counterpart): external SAT solver factories.

## Errors and panics

The bindings follow the Rust convention for errors: a call returns
`bitwuzla::Result<T>` only if it can fail for reasons the caller cannot rule
out in advance, and panics if the caller violates its contract (like indexing
out of bounds).

Calls that return `Result` (the `Error` carries Bitwuzla's error message):

- Interpreting text: `Parser` (`new`, `parse_str`, `parse_file`,
  `parse_term`, `parse_sort`), values given as strings
  (`TermManager::mk_bv_value`, `mk_fp_from_real`, `mk_fp_from_rational`), and
  option values (`Options::set`: an invalid mode, a number out of range, or a
  SAT solver that is not compiled in;
  `Options::set_by_name` and `Options::set_args` also for unknown options).
- Depending on how Bitwuzla was built or configured: `Bitwuzla::new` (e.g., a
  SAT solver that is not compiled in) and `Bitwuzla::configure_terminator`
  (not every SAT solver supports terminators).
- Solving: `check_sat`, `check_sat_assuming`, `simplify`, `simplify_term`,
  `get_interpolant`, `get_interpolants`. These fail if Bitwuzla does not
  support the formula. Bitwuzla reports this like any other error, so these
  calls return `Err` for all errors except terms of different term managers,
  including invalid arguments and calls in the wrong state (e.g.,
  `get_interpolants` without `Opt::ProduceInterpolants`).
- Opening files: `Options::set_diagnostic_output_stream`.

Everything else panics on error: invalid arguments (e.g., a bit-vector sort
of size 0, an argument of the wrong sort, terms of different term managers,
an option value of the wrong type) and calls in the wrong state (e.g.,
`get_value` without `Opt::ProduceModels` or after an unsat result, or calls
from a terminator). The panic message is
Bitwuzla's error message and the location is that of the offending call. The
objects involved remain usable if the panic is caught with
`std::panic::catch_unwind`. `Parser::bitwuzla` returns `None` while the input
has not initialized the solver yet, and `Options::option` returns `None` for
an unknown option name.

Internally, the C API reports errors by calling an abort callback. The
bindings install a callback that unwinds back into Rust (all
`libbitwuzla-sys` functions use the `"C-unwind"` ABI), where the error is
caught and returned as `Err` or raised as a panic. With `panic = "abort"`,
errors print and abort instead.
